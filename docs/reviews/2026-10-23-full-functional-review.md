# LightCMS 全功能复核：一致性、恢复能力与扩展边界

日期：2026-10-23，Asia/Shanghai。代码基线：`1d2622f0887aab5715780ea80f38a294845536ea`（main）。

本轮是审查与方案，不修改业务实现，不调整生产账号、模板、文章、Worker、域名或首页 HTML。配套方案见 [渐进式重构方案](../superpowers/specs/2026-10-23-compatible-modernization-design.md)。

后续实施状态（2026-10-23）：本报告下文保留基线发现，不代表这些问题仍未修复。R01–R07 均已有对应修复与回归测试；后续任务内核、对象存储/容量、目标维护、任务中心及备份恢复也已实现。证据与验收边界见[实施计划](../superpowers/plans/2026-10-23-compatible-modernization.md)和[操作手册](../MODERNIZATION-OPERATIONS.md)。未执行生产内容变更或报告浏览器视觉验收。

## 1. 总结

推荐保留现有系统，进行内部结构的分阶段重构，而不是换语言、换数据库或一次性重写。

上一轮模板升级、删除保护、Cloudflare 确定拒绝后的释放、纯静态别名、独立导出及按钮状态等修复确实在当前代码中，不将它们重复报告为未修复。新的主要问题集中在旧内容服务与新版 Publication/静态交付模块之间的一致性落差。

本轮列出 **7 项确定问题：4 项 P1、3 项 P2**。其中 6 项通过本地测试或故障注入确认；另外 1 项由并发时序和实际查询条件确认。另列 6 类架构/容量风险，不把尚未发生或未压测的风险写成线上事故。

最重要的发现：**测试通过不等于所有动作具备一致的事务、取消和恢复语义**。新版发布系统拥有固定快照、幂等和租约，部分旧模块仍依赖多个非事务写入、内存 goroutine 和宽松的状态更新。

## 2. 覆盖范围与结论边界

| 功能域 | 检查内容 | 当前判断 |
| --- | --- | --- |
| 内容新增、编辑、批量、版本历史 | ContentService、版本保存、CAS、调用链 | 发现主记录/历史写入不原子；批量操作会忽略历史写入失败 |
| 原站点发布、撤下、恢复、重命名 | Publication saga、幂等、快照、现有回归测试 | 应保留为唯一原站点发布权威；本轮没有证据要求推翻其状态机 |
| 模板、字段、升级、slug | 模板契约、后台适配、升级任务的冻结条件 | 上轮修复存在；模板引用删除还应纳入统一事务边界，避免未来新增旁路 |
| 片段与九套报告模板 | include、快照、影响列表、模板测试 | 不应恢复隐式重新发布；影响查询仍需索引化。本轮未重新做九套模板的全尺寸截图验收 |
| 静态导出、ZIP/HTML | 来源读取、采集、快照恢复、容量检查 | 固定 Publication 来源正确；读取阶段和多请求之间尚无统一内存预算 |
| Cloudflare 账号、凭证、目标 | 创建、核验、轮换、停用、归属、初始化 | 现有账号流程保留；域名/环境迁移、漂移恢复、撤下/回滚仍缺完整管理闭环 |
| Worker 上传、激活、校验、历史 | assets-only、请求分批、检查点、错误处理 | 纯静态方向正确；长路径重定向检查不足，任务错误可见性需要增强 |
| 审批 | 提交、决定、取消、阈值、内容关联 | 发现重复投票和取消后的标记残留；流程规则还应冻结到审批请求 |
| 定时发布 | due 查询、权限/审批过滤、幂等键 | 已使用发布服务和稳定 key；应升级为可观测、可恢复的任务而非仅靠周期查询 |
| RSS/CSV/Markdown 导入 | 后台执行、日志、取消、完成落库 | 取消不能阻止后续执行；内存任务缺少重启接管 |
| 内容分支、沙箱、合并 | 草稿合并、部分失败、最终状态 | 不自动发布的边界正确；部分失败却将整个分支标记 merged |
| 编辑锁 | 获取、续租、释放 | 获取锁有先读后删的竞争窗口；这是编辑协作锁，不等于 Publication 的发布锁 |
| 素材、主题、文件夹、合集、重定向 | 服务/后台入口及版本依赖 | 删除与引用关系缺少统一管理；应纳入资源依赖图，不能用简单全站重生成为替代 |
| 搜索、索引、智能助手、MCP、CLI | 入口复用、异步索引、角色/会话上下文、现有测试 | 建议统一命令层、任务与可选能力降级；未真实调用付费模型或外部搜索服务 |
| Webhook、通知、统计 | 内存异步与 durable outbox 两种路径 | 发布事件有 durable 路径，普通内容事件仍有进程退出/请求取消丢失风险；统计缓冲是另一种可接受但需声明的精度边界 |
| 用户、会话、API key、治理 | 权限上下文与业务入口复用 | 保留现有契约；本轮不是渗透测试，也没有修改既定凭证保存策略 |
| CI、部署、健康、备份 | workflow、测试环境、health、运行手册 | 门禁已增强；健康还不能证明所有后台工作正常，数据恢复演练不能只用镜像回滚代替 |

“覆盖”指功能入口、关键服务和异常路径的审查，不代表每一个分支、每一种浏览器、每个线上集成都执行过端到端测试。

## 3. 确定问题

### R01 / P1：内容主记录与历史版本可能出现半完成写入

位置：`internal/services/content.go:313`、`:439`、`:521`、`:563`、`:672`、`:690`、`:1272`。

- Create/Update 先写 content，再调用 saveVersion；第二步失败时，返回错误并不会撤销已写入的 content。
- BulkCreateContent 的历史 InsertMany 错误被忽略，仍返回单项 Success=true。
- 本地服务层故障注入确认：更新历史写入失败，服务返回错误，但标题已更新，current_version 已增加，而对应历史不存在；批量新增则直接报告成功，却没有历史。
- 影响：重试语义不清、历史还原缺失、后续基于版本号的发布与审计无法获得完整记录。不是已有发布 HTML 立即被覆盖。

建议：单篇 content CAS、版本插入、必要的业务 outbox 在同一事务提交；批量保留逐项部分成功，但单项内部必须完整。只有事务成功才返回成功、发送索引任务和通知。不得简单删除版本校验来绕过缺口。

验收：注入每一处写入失败后，主记录与版本要么都变，要么都不变；同 key 重试不重复增版本；多项批量失败只影响对应项。

### R02 / P1：取消导入只更新状态，后台仍可能继续写内容

位置：`internal/services/import.go:245`、`:373`、`:519`、`:608`、`:658`。

- 运行循环使用独立 context.Background，没有读取取消状态或共享取消信号。
- CancelJob 把记录标记 cancelled，但 finalizeJob 只按 `_id` 更新，可以将 cancelled 覆盖为 done。
- 本地确认：运行中的记录取消后，执行实际 finalizeJob，最终状态变回 done。结合循环无取消检查，可以确定取消没有形成执行屏障；本轮未向真实 RSS 源发送导入请求。

建议：先持久化 cancel_requested，逐项执行前检查，执行器进入 cancelled；完成写入用状态/租约 CAS。已经提交的项不暗中撤销，清晰显示“已完成 N 项，余项已取消”。发布已产生不可逆意图时单独进入核实阶段。

验收：取消后不再开始新项，完成回调不能覆盖终态；重复取消幂等；中途重启仍能保留取消决定。

### R03 / P1：同一审批人重复批准可以累计成多票

位置：`internal/services/approval.go:246`、`:279`、`:291`、`:315`；入口 `internal/handlers/api_approvals.go:292`。

- 每次都 `$push` 一条 decision，统计 decision 数量，没有按审批人去重。
- 本地确认：需要两票的三人并行审批，同一人批准两次，状态变为 approved。
- 决策写入过滤器只有 `_id`，并发决定之间缺少状态/步骤版本保护。
- 补充语义问题：默认“多数”用 `(n+1)/2`，偶数人数时等于半数而非严格多数；执行时又读取可修改 workflow.Mode。阈值及规则应明确并冻结，而不是仅依靠注释。

建议：以 request、审批人和步骤构成幂等身份；事务中检查 pending、步骤、唯一决定和阈值。冻结审批对象的内容版本及工作流快照。审批仍只更新审批状态，不能恢复自动发布。

验收：双击、HTTP 重试、同人多 key 均只算一票；不同人并发不会丢票；并发批准/拒绝只产生一个合法终态；旧请求的规则不随工作流编辑漂移。

### R04 / P1：分支部分合并失败后仍封存为 merged，无法重试失败项

位置：`internal/services/fork.go:243`、`:281`、`:330`、`:365`。

- 各项失败追加到 Failed 后继续执行，但最终无条件把分支标记 merged，且忽略该更新错误。
- 本地注入新草稿写入失败：Failed 非空，分支仍为 merged；再次 Merge 被“不是 active”拒绝。
- 影响：成功项和失败项混杂，用户无法通过同一合并流程继续处理剩余内容。

建议：持久化每项结果，引入 partially_merged/merge_failed；重试只处理未完成项。完全完成才进入 merged。保留现有“只合并草稿、需显式发布”语义；已有 fork-wins 策略若调整，必须增加版本化/显式选择，不偷偷变更旧接口。

验收：第 N 项失败、进程退出、重复请求均不重复覆盖已完成项；成功项不丢失，失败项可继续；原站点发布快照不变化。

### R05 / P2：取消审批未清除关联内容的 pending_approval

位置：`internal/services/approval.go:390`；定时发布过滤 `internal/services/scheduler.go:64`。

- Cancel 只更新 approval_requests。
- 本地确认：取消后内容 pending_approval 仍是 true。
- 影响：审批已经不存在于待办，但内容仍显示/被判断为待审批，定时发布等会继续跳过。不能通过无条件清 false 修复，因为可能有更新的待审批请求。

建议：将请求取消与“是否还有其他有效待审批请求”的关联状态更新放在同一事务，使用当前请求关联 ID/CAS；无匹配记录和非法状态返回明确结果。

### R06 / P2：编辑锁获取的先查后删会删除刚被他人取得的锁

位置：`internal/services/lock.go:42`、`:61`、`:71`。

确定的竞争时序：A/B 均读到无锁；A 插入成功；B 随后执行只按 content_id 的 DeleteOne，删掉 A 的新锁，再插入自己的锁。唯一索引不能阻止这段时序，因为删除在插入之前。此项由代码时序确认，没有将概率性并发压力运行冒充确定复现。

建议：用单条条件更新/有界事务获取；条件只能是不存在、过期或同一 owner，续租/释放带 lease token。不要因此更换原有 Publication 页锁协议。

### R07 / P2：原生别名规则缺少单行长度校验

位置：`internal/product/staticdelivery/assets_first.go:100`、`:111`。

- 当前检查规则总数，但没有检查 URL 编码后每行长度。
- 本地构造合法多段路径，生成的规则长 1146 字节，函数仍成功。
- Cloudflare 文档规定单条 `_redirects` 声明最多1000字符，且不合法规则可能被忽略。这里产生的编码后字符串是 ASCII，字节数即字符数。未在生产验证平台拒绝/忽略的具体响应。
- 另一个已知容量边界：每篇通常生成两条别名，因此带首页时，999篇普通非根文章已用1999条规则，再加一篇会达到2001条，早于目标的20000文件容量。这是当前策略边界，不是假称平台仅支持1000篇文章。

建议：预览时展示文件、别名数量、最长规则、包大小的完整预算；对长路径给具体诊断。不能通过启用 JS 兜底或静默丢弃既有别名来解决。超过预算时选择经过验证的原生布局、分站点，或显式配置外部规则；成本与行为变化均需用户确认。

依据：[Cloudflare 重定向限制](https://developers.cloudflare.com/workers/static-assets/redirects/)。

## 4. 架构与容量风险：不等同于已发生故障

### A1：任务执行系统分裂

Cloudflare 有 Mongo 租约、持久化检查点；导入依赖内存 goroutine；RegenQueue 依赖64容量 channel，启动只消费 channel，不恢复数据库 pending/running；普通 Webhook 也有内存异步路径。重启恢复、取消、进度、错误含义不一致。

证据：`internal/services/import.go:245`；`regen_queue.go:44`、`:89`；`webhook.go:77`；`internal/product/staticdelivery/runner.go:80`。另外，当前 RegenQueue 已不实际发布，但日志/状态仍称 regenerated/done，容易误读。

### A2：单包上限不等于进程内存上限

128MiB源预算、256MiB公开包、512MiB私有快照是单操作限制；HTTP 预览不受 Runner 并发槽控制，能并发 Load 当前 release 和多份导出。Documents 先加载每份资源，再 Collect；gob 写盘不意味着 gob 编码内部没有大缓冲。没有本轮峰值内存测量，不能断言已OOM，也不能承诺1GiB机器一定够用。

证据：`staticdelivery/commands.go:202`、`:242`；`release_store.go:120`、`:215`；`staticexport/snapshot.go:33`。应统一容量准入、磁盘流式对象读取和进程级背压。

### A3：私有存储只增长，引用生命周期未闭环

每次预览保存完整 release；保留天数配置存在，但没有完整引用保护GC。成功、失败、过期预览、回滚保留、任务冻结、临时目录、备份之间没有统一资源目录。单纯按 mtime 删除会破坏恢复。

证据：`staticdelivery/config.go:63`；`commands.go:202`；`release_store.go:77`；现有运维文档明确列出未交付部分。

### A4：大文件中的入口重复与契约漂移

当前 handlers.go 7132行、admin_templates.go 10008行、content.go 2325行、main.go 1051行。行数本身不是缺陷，但后台/API/MCP/后台任务各自处理部分业务规则，已经出现上轮模板删除旁路、本轮状态更新不统一的问题。

应按业务模块拆包、按命令统一业务，不为“现代化”强行重写成SPA或微服务。

### A5：操作页面查询与依赖管理仍需优化

片段影响查询扫描所有模板和非分支内容的 data，且为每个名字重复编译 regexp；限制展示50篇没有限制扫描量。普通模板影响查询也加载不需要的 data。当前数量少时可能没有问题，增长后会拖慢编辑入口。

素材删除目前没有统一的内容/历史/发布引用保护。建议将其与模板、片段、页面依赖纳入同一可查询依赖图，区分“停止使用”“从编辑库删除”“从历史产物回收”。

证据：`internal/handlers/template_impact.go:31`、`:78`、`:117`；`internal/services/asset.go:221`；后台素材删除还有独立实现 `handlers.go:5665`。

### A6：有健康接口，但缺少后台任务服务目标与恢复证据

`/health` 检查 goroutine 数量和DB；`/healthz` 有DB及迁移信息。它们不能证明队列有进展、磁盘可写、导出没有堆积、Worker 校验可恢复。Runner 主循环丢弃 RunOnce 返回值，部分异常没有进入用户任务错误或结构化日志。

证据：`cmd/server/main.go:906`；`internal/handlers/healthz.go:65`；`staticdelivery/runner.go:67`。不建议把每次健康探针变成对所有公开Worker页面的轮询；改为被动状态指标和按需/有界验证。

## 6. 建议结论

先修业务动作的一致性，再统一任务与依赖存储，最后整理后台入口。所谓激进应是大胆减少重复实现、明确权威数据和状态机；不应是同时替换数据库、前端框架、发布协议和生产数据结构。
