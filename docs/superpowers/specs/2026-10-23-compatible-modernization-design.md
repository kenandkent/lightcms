# LightCMS 兼容现有功能的渐进式重构方案

日期：2026-10-23。基线：main `1d2622f`。状态：**十项实施任务已在本地实现并通过分层验证；按用户授权在测试与构建通过后提交推送 main，生产部署状态单独确认**。

对应审查：[全功能复核与问题证据](../../reviews/2026-10-23-full-functional-review.md)。用户已要求修复所有问题并按本方案重构；本文件不是实现或上线完成声明。逐项进度见[实施计划](../plans/2026-10-23-compatible-modernization.md)，预算与 SLO 仍须以实际测试结果验收。

实施验收补充：核心流程已完成本地单元/集成、并发、构建和原生静态协议验证，具体证据和范围见实施计划及[操作手册](../../MODERNIZATION-OPERATIONS.md)。用户要求不在本机打开报告，因此未做报告浏览器视觉验收。容量额度是准备任务预留，不是整个进程 RSS 的硬限制；备份采用显式离线恢复点；依赖索引是有时间戳的保守清单，不能作为发布或删除权威。生产/外部付费服务不在本轮验证声明中。

## 1. 目标、非目标与方案选择

目标：让当前每个功能在成功、失败、取消、重试、并发、进程重启和外部平台不确定响应下都有明确结果；减少重复数据和重复业务逻辑；让用户能看懂当前发布到了哪里、能否继续、失败后如何处理。

不做：更换 Go/MongoDB、取消现有功能、强制迁移全部文章、自动重新发布历史内容、修改当前 Worker 域名、为公开页面重新加入 JavaScript 404、默认为所有用户增加运行依赖或付费服务。

| 选项 | 收益 | 主要代价 | 建议 |
| --- | --- | --- | --- |
| 只修单点 | 快速降低已知故障 | 多套状态机和旁路继续增加 | 仅用于第一阶段止损 |
| 模块化单体、统一命令/任务/对象存储 | 保持部署简单，同时系统性解决一致性和恢复 | 需要契约测试与逐模块迁移 | **推荐** |
| 全面重写前后端并拆微服务 | 可重新设计所有边界 | 同时引入网络事务、数据迁移和大范围UI回归 | 当前不建议 |

激进的部分是重做内部边界和数据生命周期，不是强迫用户重新学一套系统。后台前端是否引入 TypeScript 构建作为独立评估项，不作为这轮正确性修复的前提。

## 2. 不可破坏的兼容性约束

1. 保留原 API/MCP/CLI/后台的入口、字段含义、权限规则及已公开错误码。新响应先增加字段；改变含义需版本化。
2. Content 是编辑态，ContentVersion 是历史，Publication 是原站点发布权威，StaticRelease 是 Worker 的独立副本。四者不能合并成一个 published 布尔值。
3. 原站点发布、Worker 发布是独立动作。原站点撤下不自动删除 Worker 副本；目标归档不等于远端下线。
4. 历史快照不得用今天的模板、片段或素材偷偷补渲染。旧 gob/导出包继续可读，缺失必须明确报告。
5. 已有 URL、中文路径、独立 `.html` 页面、别名、社交元数据、模板字段、语言适配和 loading 行为建立基线，未经确认不改变。
6. 首页 `umx-home.html`、生产模板内容、域名绑定不是代码重构的附带变更对象。
7. 不移除现有发布 saga、CAS、唯一索引、幂等与不确定激活保护。不能用“失败后直接解锁”掩盖远端可能已激活。
8. 不改变用户已经选择的 Cloudflare 凭证保存配置要求；不重新强制服务器配置加密密钥。日志与页面仍不得暴露 Token。
9. 不删除已有编辑协作锁、审批、导入、统计、搜索等功能；旧接口继续委托到新实现。
10. 本方案不授权执行生产GC、迁移、撤下或回滚，这些操作仍需明确的预览和确认。

## 3. 目标模块结构与权威边界

仍使用一个主要 Go 服务、MongoDB 和私有文件存储。后台任务可先在同一进程运行，后续根据实际负载拆出同一代码构建的 worker 进程，而不是先拆成多套微服务。

| 模块 | 唯一职责 | 不应该做的事 |
| --- | --- | --- |
| Authoring | 内容/版本原子写入、草稿、路径和字段验证 | 直接写公开 HTML |
| Template & Dependency | 模板版本、片段解析、依赖与影响查询 | 保存时自动覆盖已发布内容 |
| Workflow | 审批、分支合并、导入计划、取消与逐项结果 | 擅自代替用户执行发布 |
| Publication | 原站点生成、激活、撤下、恢复、发布 outbox | 直接管理 Cloudflare 站点 |
| Static Delivery | 固定导出、预览、目标发布、远端核实、撤下/回滚 | 回源读取可变编辑态替代历史产物 |
| Jobs | 通用租约、幂等、进度、取消、重试和事件 | 统一掉各业务独有的状态机 |
| Artifact Store | 对象、清单、引用、保留、校验和回收 | 按文件年龄直接删当前版本 |
| Read Models | 列表、搜索、依赖图、状态摘要、统计 | 作为发布成功的最终权威 |

后台、REST、MCP、CLI、智能助手是适配器。所有关键写操作调用同一命令服务；数据库直写仅留在受约束的 repository 中。逐模块迁移，避免一次移动数千行同时改变行为。

## 4. 第一优先：修复确定的一致性问题

### 4.1 内容和版本

单篇编辑事务包含：读取/验证期望版本、CAS 更新内容、插入对应版本、写入后续索引/事件意图。成功响应只在事务提交后返回。

- 现有不携带期望版本的客户端保持兼容；新增编辑UI发送 expected_version/If-Match，新API可要求显式版本。不能立即让所有旧客户端请求失败。
- 批量操作继续逐项部分成功，但每项内部采用同样事务，返回逐项错误码、是否已提交、当前版本。
- 迁移前只读扫描内容版本缺口，产出修复报告。不得伪造缺失历史：无法重建的旧版本标为缺失；可从可靠快照恢复的，明确记录来源和迁移事件。
- 保存和发布是不同的幂等动作，不能共用一个 key 或一个成功状态。

### 4.2 审批

请求冻结 content_version、工作流版本、审批人、步骤、阈值与规则。决策以 request_id + step + actor_id 唯一，重复提交返回同一结果。

- 并行阈值明确使用“至少几票”；若界面称严格多数，则默认 `floor(n/2)+1`。对已经有可信规则快照的旧请求保持其明确规则，不能中途改变阈值。旧记录缺少规则/内容版本快照时，标记需要重新确认或重新提交，不能用今天的workflow冒充当初的规则。
- 批准/拒绝/取消用状态与 revision CAS；关联 pending 标记在事务中更新，不能覆盖更新的审批请求。
- 审批期间内容改变，显示“审批针对旧版本”，用户重新提交或明确回到已批准版本。
- 审批通过不自动发布，继续保留现有显式发布边界。

### 4.3 导入与分支合并

- 导入先生成持久化输入清单和逐项身份，不把原始大CSV直接放进Mongo单条文档；解析结果分片保存并引用。
- 取消是停止未来工作，不是假装回滚已经成功的项。终态 CAS 防止取消被后续完成覆盖。
- 分支合并逐项持久化 base_version、结果版本、错误与幂等 key。存在失败项时进入 partially_merged，可重试；成功项不再重复更新。
- 继续保留 fork-wins 的旧接口语义；新的预览可推荐“冲突时暂停”，但必须由调用者显式选择 policy，不静默改变旧行为。
- 所有合并只更新草稿，后续发布另行确认。

### 4.4 编辑锁

使用条件获取/续租和 lease token；只有锁不存在、已过期或同一个持有者时可更新。释放和续租带 token，禁止误删新持有者。协作锁不是存储事务的替代物。

## 5. 统一持久化任务内核

建议新增可版本化的 jobs/job_items/job_events 结构，先接入导入和合并，再整合升级任务及其他后台工作。Cloudflare 的外部激活状态继续由其专用执行器维护，不把所有任务塞进同一套简单成功/失败枚举。

共同字段：kind、schema_version、actor快照、输入快照引用、idempotency_scope/key_digest、state、revision、lease_owner/fencing_token、lease_until、cancel_requested、deadline_at、progress、next_run_at、error_code、可公开诊断、关联资源ID。

要求：

- 数据库声明任务是唯一提交点；内存 channel 只用于唤醒，不是任务真相。
- 接管必须增加 fencing token，所有后续写入校验 token；租约过期的旧执行器不能提交。
- 消费者有界并发、有界待处理数量、队列公平性。不能仅限制执行中的 goroutine，而让等待 goroutine 无限增长。
- 每项执行前核实取消、权限/账号状态及冻结输入；恢复已有外部动作与发起新动作分开授权。
- 不吞掉数据库更新错误或 MatchedCount=0；统一把可公开原因写入任务事件，完整受控诊断留在日志。
- 当前“提交起5分钟”的期限继续保留；UI区分排队、执行、超时核实。要改成“开始执行后5分钟”必须另行批准，不在重构中偷偷延长。
- 审计与普通内容Webhook改用事务 outbox；现有发布 outbox 保留事件ID去重契约。

### 同一 Worker 的并发与串行

不同 Worker 可并行；同一 Worker 的全站版本激活必须有序，不能无条件并发覆盖。

推荐新增“允许排队的发布意图”协议：冻结选中文章及目标配置，记录每个变更路径的期望版本/哈希；执行时合并其他任务新增但与本任务无关的路径。任何同路径冲突或目标配置变化都要求重新预览，不自动选择赢家。

这是新能力，必须使用显式 queue_mode 或新接口。旧接口继续保持现有 expected_revision 严格检查。不能让旧确认摘要在排队时无限制自动重基准。任务事件中记录真实合并基线、保留路径和最终release。

### 不确定外部结果

明确拒绝：失败并释放。网络超时/未知激活：停止新写入，进入只读核实。人工恢复不是强制删锁，而是有远端状态证据的专用命令；没有足够证据时，不提供“假定未发生”的按钮。

## 6. 私有产物与大文件路径

建议引入内容寻址对象存储：同一 SHA-256 对象只存一份，release/export 清单引用对象。先实现本机文件后端，不默认引入 R2/S3 等新账户或成本。

新结构示意：对象目录按 hash 分层；清单记录 schema_version、来源Publication、页面路由、对象引用、MIME/size/hash、目标配置、构建器版本。旧包由旧 reader 继续读取。

- 原始源文件、渲染结果、公开资源和依赖清单分离；不要把整个站点以及所有原始资源重复塞入一个 gob。
- 采用 Open/Stat 接口逐块读写/上传。单文件完整读入只用于明确需要的HTML/CSS解析，受预算约束。
- 预览改成可恢复的准备任务；HTTP不承担长时间全站构建。与用户现有“一次点击预览自动准备”交互保持一致。
- 对每个作业按估计内存/磁盘占用申请容量配额；进程同时准备多个128MiB包时要排队或拒绝，不以goroutine数量代替内存预算。
- 摘要读取与发布验证读取使用不同类型，不用同一个含空 Data 的 ReleaseManifest 假装两者可互换。
- 老gob按需迁移，先读、验证、转换到新清单；默认不删除原件，完成恢复演练后再纳入GC。

### 引用保护 GC

新增资源目录和明确生命周期：available、pinned、deleting、deleted；删除墓碑和幂等记录分开保留。

保护根至少包括当前release、非终态任务、有效预览、回滚保留集、人工pin、迁移中记录、备份中的固定清单。计划计算和执行删除之间必须重新核实引用，并与新任务创建引用通过同一事务/fencing机制竞争，避免检查后被新任务引用。

顺序：用量统计 → dry-run候选及原因 → 用户确认摘要 → 事务标记deleting → 删除指定对象 → tombstone。中途重启可接续；删除失败不假报成功；新引用不能指向deleting对象。

初版只提供手动确认清理。自动清理由管理员明确开启并保留相同保护机制。不得删除操作幂等账本来回收空间，也不得仅按mtime清理 `.building-*` 而不检查相关运行租约。

保留期初始沿用现有可配置值：一般私有包90天、失败包7天；仅“达到保留期且不再被保护引用”的对象有资格进入清理预览。pin没有自动过期，解除须显式操作。先删除过期清单引用，再计算对象可回收性，防止把所有历史引用永久当作保护根，也防止跳过有效回滚/备份清单。

## 7. Cloudflare 目标维护闭环

统一使用 preview → confirm → durable job → verify → commit 的命令模式。

| 操作 | 预览与前置检查 | 提交原则 |
| --- | --- | --- |
| 更换公开域名 | 域名已经绑定同一专用Worker，HTTPS/ownership核验，列出canonical/OG等变化 | 从固定源快照重写元数据并建新release；公开验证通过后原子提交origin/config_revision |
| test转production | 明确列出robots与索引策略变化，要求显式确认 | 新release验证后提交环境，不只修改数据库字符串 |
| 撤下选定页面 | 显示路径、受影响页面和将保留的页面/资源 | 整站新版本去除路径；GET/HEAD验证预期404，引用资源按保留规则处理 |
| 单篇回滚 | 选择历史Publication/静态页面快照，显示与当前差异 | 冻结历史内容合入当前其他页面；不用今天的模板重渲染历史正文 |
| 整站回滚 | 展示增加、替换、撤下路径及配置差异 | 生成新的回滚操作记录；不直接覆盖数据库current_release_id |
| 漂移恢复 | 显示本地记录、远端版本、owner和可验证清单 | 仅接受可证明归属的已知版本；未知站点禁止接管 |

失败时分别记录“外部状态已变/未变/未知”和“本地配置已提交/未提交”。如果远端激活成功但验证失败，不能把数据库旧origin继续显示为新版本已完成；UI应展示待核实的候选地址。

域名绑定仍由用户在Cloudflare管理，除非另行授权自动管理DNS。不能默认新增所需域名权限。

### 原生路由预算

检查所有规则的数量、编码后长度、通配符/占位符语义、显式页面优先、中文路径、查询参数。已有别名继续保留；禁止为扩大容量静默取消别名。

在2000静态规则上限下，先提供容量诊断和目标分片方案；是否启用Bulk Redirects须独立验证套餐、配额及权限，不承诺免费无限规则。正常页面和404继续由平台静态资源处理。

依据：[重定向规则](https://developers.cloudflare.com/workers/static-assets/redirects/)、[静态资源计费](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/)。

## 8. 后台与接口：减少用户猜测

保留已有路由和菜单，先按功能拆出 Go 模板/脚本文件，配套模板转义与CSRF测试。不要为文件拆分同时修改表单字段、API和交互逻辑。

推荐逐步增加：

- 内容列表分别显示草稿版本、原站点发布版本、各Worker发布版本，明确“有未发布更改”。
- 独立任务中心按导入/审批/升级/导出/发布筛选；所有页面跳到同一任务详情。
- 任务详情展示阶段、已完成项、错误原因、下一步动作、来源快照、目标、可复制分享地址和验证时间。
- 成功链接始终来自已验证release，不根据当前可变域名猜测。预览地址标记为候选，不能混作发布成功地址。
- 操作按钮由明确状态决定，不依赖多个分散的DOM赋值；用页面状态机覆盖重复点击、刷新恢复、网络中断、权限变化和切换目标。
- 依赖图维护 template/snippet/asset → content，以及 Publication 的冻结依赖。编辑页只读取索引和分页摘要；扫描重建在后台进行。
- 查询索引需要 revision/更新时间及“索引尚未追上”提示，不能将过期计数显示成强一致事实。
- 通用错误显示可操作说明和任务ID；完整内部诊断不回传Token或大响应体。

API兼容测试覆盖后台、REST、MCP、CLI和智能助手对同一业务动作的结果一致性。OpenAPI作为新增协议的契约来源，旧手写说明明确哪些内容属于历史版本。

## 9. 可观测性、备份与性能目标

建议添加：队列深度/最老等待时长、执行心跳、失败/取消/未知激活数、预览耗时、每阶段字节量、对象存储用量、GC候选数、外部请求次数及原因、进程RSS与容量等待时长。

健康检查分为进程存活、核心服务可用、可选能力降级。Cloudflare暂时不可用不能让CMS读写整体宕机；外部AI或邮件失败也应独立显示。公开页面不因后台监控而周期性全站抓取；验证由发布/恢复动作触发，后续外部可用性监控另行明确频率和预算。

以下是建议验收目标，不是当前实测值：

- 确认命令应快速返回持久化job ID，长工作转异步。
- 正常本机条件下，列表/任务状态等轻量请求p95目标低于500ms；根据生产基线调整，不以牺牲完整性实现。
- 峰值RSS受已配置内存预算约束，超预算任务排队/拒绝，不由系统OOM终止。
- 取消后在下一工作项开始前生效；已经提交项有明确清单。
- 服务重启后，在规定的租约恢复窗口内继续或明确失败，不永久停在running。
- 发布核实保留所有字节、MIME、缓存与归属检查，不把“抽样通过”偷偷改为“全站发布成功”。

备份必须同时覆盖Mongo记录、私有对象/清单和必要配置。记录同一恢复点及对象清单，先冻结manifest引用，再备份其对象。定期在隔离环境恢复，校验随机历史页面、当前release和未完成任务；“旧镜像还能启动”不是数据恢复验证。

## 10. 分阶段实施与退出标准

| 阶段 | 内容 | 阶段完成标准 |
| --- | --- | --- |
| P0 兼容性基线 | 接口/错误码/页面/模板/历史包样本，回归矩阵，备份恢复点 | 当前行为可重复验证；旧缺陷标成待修而非黄金行为 |
| P1 一致性止损 | R01–R07；审批快照/去重；取消/部分结果；编辑锁 | 故障注入、并发和重试测试通过；无隐式发布 |
| P2 命令和任务内核 | 导入、分支、升级、普通Webhook迁移；统一诊断 | 终止进程后能恢复；各项进度与幂等记录匹配 |
| P3 存储与容量 | 对象存储、流式读取、预览异步化、依赖索引、GC预览/确认 | 新旧包均可读；引用竞争不误删；压测不越预算 |
| P4 发布目标维护 | origin/environment迁移、撤下、回滚、漂移恢复、可选排队协议 | 每个动作都通过成功/失败/未知/重启四类验证 |
| P5 后台与运维收口 | 任务中心、版本状态、接口契约、监控与恢复演练 | 用户可不看日志完成正常操作，并按提示恢复失败 |

可以并行做无共享状态的测试和只读索引工作，但有外部激活和GC的阶段按依赖推进。每阶段单独可交付、可停止；不在一个大提交中同时重写全部功能。

## 11. 迁移与回退策略

- 数据结构使用 expand → backfill/dual-read → switch → observe → contract。先增加新字段和reader，不先删旧字段。
- 影子运行仅允许无副作用的解析、验证、差异计算；禁止让新旧路径都实际发Webhook或激活Worker。
- 内容命令一次只能有一个权威写入路径；不能靠双写两个可变副本解决事务问题。
- 老任务由旧执行器排空或显式接管，不能把状态名简单映射后重发外部请求。
- 老导入/合并任务如果缺失足以恢复的冻结输入或逐项结果，必须进入“需人工确认”，给出已完成项核对工具；不能猜测断点并直接重做。新任务从第一天写全恢复信息。
- 当前部署有单实例保护，首批灰度可采用按操作类型/内部账号的功能开关；不能贸然同时启动两个可写发布实例。
- 回退前确认旧版本能读新数据、任务和清单。新数据已产生后，必要时先停写/排空新任务，再切兼容reader；禁止只回滚镜像而不考虑数据格式。
- GC和破坏性目标操作最后开启，并且提供试运行结果、审计记录、保留窗口与明确的不可恢复提示。

## 12. 完整验收矩阵

每个写功能至少验证：合法成功、非法输入、无权限、重复请求、请求超时但已提交、数据库故障、进程退出、并发同资源、并发不同资源、取消、部分成功、重试、历史兼容。

还需专门验证：

1. 九套模板的桌面/手机、中英、长标题、表格/代码块、空字段、社交元数据、loading和嵌入片段。
2. 内容新增/编辑/批量与历史记录一一对应；草稿保存不会改变任何现有公开页面。
3. 原站点发布/撤下/恢复/rename 与 Worker 互不隐式影响。
4. Worker 原生根路径、中文、无后缀、独立.html、别名、查询参数、404、GET/HEAD/304和缓存。
5. 长URL/临界规则数、25MiB边界、总资源预算、同时多账号任务、超大导入、磁盘写满。
6. 模板/片段/素材更新及删除不破坏冻结历史；GC与新引用创建交错测试。
7. 旧导出和gob包、旧API客户端、旧确认摘要/过期摘要、旧幂等记录的兼容。
8. API Token撤销、角色变化和目标停用：新操作被阻止，已发出的不确定操作仍可只读核实。
9. 第三方服务使用契约测试/本地模拟为常规门禁，真实Cloudflare验收仅使用专用目标并明确授权；不覆盖现有首页或正式报告。

## 13. 推荐执行顺序

先批准本方案的边界与分期，然后将P1细化成逐项实施计划。优先修 R01内容事务、R02导入取消、R03审批去重、R04部分合并；同时建立契约基线。再交付统一任务内核，随后实现尚未完成的GC及目标生命周期能力。

不建议直接从“换前端框架”或“拆微服务”开始，也不建议把所有优化压进下一次生产发布。兼容性不是口头保证，而是上述基线、迁移、故障注入、灰度及回退机制共同提供的可检查证据。
